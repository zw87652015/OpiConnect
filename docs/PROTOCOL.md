# OpiConnect Protocol

Authoritative spec for pairing, key derivation, encryption, the BLE link and the relay HTTP API.
Implementations: watchOS (Swift/CryptoKit), Android (Kotlin), relay (Node 22, `server/index.mjs`).
Test vectors: `docs/test-vectors.json` (generated by `docs/gen-test-vectors.mjs`).

## Notation

- `base64url` = RFC 4648 base64 with the URL-safe alphabet and **no padding**, everywhere.
- All multi-byte integers in this document are inside JSON (decimal) unless stated otherwise.
- `sha256(x)` is the raw 32-byte digest; `utf8(s)` is the UTF-8 encoding of string `s`.

## Pairing

The watch generates a **master key `K`**: 32 random bytes from a CSPRNG. It keeps `K` in the
Keychain (app-group access group, shared with the Notification Service Extension).

The watch displays a QR code containing the string:

```
opi1:<base64url(K)>        // 5 + 43 = 48 chars
```

The Android app scans it, checks the `opi1:` prefix, decodes `K` (must be exactly 32 bytes) and
stores it wrapped by an Android Keystore AES key.

## Key derivation (HKDF-SHA256, RFC 5869)

`HKDF-SHA256(ikm=K, salt="", info=<ASCII label>, L)` — the salt is the **zero-length** string
(not absent, not 32 zero bytes; implementations must pass a zero-length salt to the expand step
per RFC 5869, i.e. `extract` uses a salt of `HashLen` zero bytes when none is provided — passing
an empty salt to a standard HKDF API produces exactly that).

| info (ASCII) | length L | result |
|---|---|---|
| `"opi/id"`   | 16 | `pairId`  = base64url(16 bytes) = **22 chars** |
| `"opi/auth"` | 32 | `secret`  = base64url(32 bytes) = **43 chars** |
| `"opi/enc"`  | 32 | `encKey`  = 32 raw bytes, AES-256-GCM key |

`pairId` and `secret` are sent to the relay; `encKey` **never leaves the devices**. The relay
stores only `sha256(secret)`.

## Encryption (seal / open)

`seal(plaintextBytes)`:

- AES-256-GCM with `encKey`.
- Nonce: 12 random bytes, generated per message.
- AAD: none.
- Output bytes: `nonce (12) || ciphertext || tag (16)` — identical layout to
  `CryptoKit.AES.GCM.SealedBox.combined`, so on Swift use `SealedBox(combined:)` directly.
  On Android/JCE: `cipher.doFinal` output is `ciphertext||tag`; the wire format is
  `nonce || that output`.

- Over JSON/HTTP the sealed bytes are `base64url`-encoded.
- Over BLE they are sent as raw bytes inside chunks (below).

`open` reverses it: split off the first 12 bytes as the nonce and the last 16 as the tag.
Anything that fails to open is discarded silently.

## Notification id

```
id = base64url(sha256(utf8(sbn.key)))[0..22)   // first 22 chars
```

where `sbn.key` is `StatusBarNotification.getKey()` on Android. 22 chars ≈ 132 bits of the
digest — collision-free in practice and valid as an APNs `apns-collapse-id` and a UNNotification
identifier.

## Notification payload (plaintext, UTF-8 JSON)

```json
{"i":"<id>","p":"<package>","a":"<app label>","t":"<title>","b":"<body>","w":1699000000000,
 "x":[{"l":"<action label>","r":true}]}
```

- `w` = `postTime` in milliseconds since epoch.
- `x` = optional action list; `r` = the action has a `RemoteInput` (watch shows a text field).
- Fields with empty strings are still present.

**Removal payload** (plaintext): `{"i":"<id>"}`.

Both payloads may optionally carry `"bt"` (phone battery 0–100) and `"bc"` (charging bool)
so pushes keep the watch's battery display fresh even over APNs.

**Size limit:** APNs alert payloads are capped at 4096 bytes. Before sealing for a relay push,
Android truncates `b` so that `base64url(sealed(payload)).length <= 3000` (which is also the
relay's hard limit on `c`).

## BLE link

- GATT service UUID: `6f70690a-0001-4c6f-9e2b-6f7069636f6e`
- `TX` characteristic (indicate, phone → watch): `6f70690a-0002-4c6f-9e2b-6f7069636f6e`.
  Indications, not notifications: the watch confirms each chunk at the ATT layer and the phone
  sends the next chunk only after `onNotificationSent`. With unacknowledged notifications, large
  messages (`cal`, ~170 chunks) overran the watch and chunks were silently dropped.
- `RX` characteristic (write with response, watch → phone): `6f70690a-0003-4c6f-9e2b-6f7069636f6e`

Roles: the phone is the **GATT server + advertiser** (Android supports peripheral mode); the
watch is the **central** (watchOS only supports central).

### Message framing

Each message is UTF-8 JSON, sealed with `encKey`, then split into chunks:

```
chunk = [flag byte] || [up to (maxLen - 1) bytes of sealed data]
flag: 0x01 = more chunks follow, 0x00 = last chunk
```

- Phone → watch: `maxLen` = negotiated ATT MTU − 3.
- Watch → phone: `maxLen` = `peripheral.maximumWriteValueLength(for: .withoutResponse)`
  (= ATT MTU − 3). Writes still use `.withResponse`; using the `.withResponse` limit would
  let CoreBluetooth issue prepared writes, which the GATT server does not support.
- The receiver concatenates the data parts until a `0x00` flag, then opens the sealed bytes.
- If the whole sealed message fits in one chunk, that single chunk has flag `0x00`.
- A zero-length sealed message is impossible (seal output ≥ 28 bytes), so the last chunk always
  carries data.

### Messages

`"type"` discriminates. Unknown types are ignored.

Watch → phone:

| type | fields | meaning |
|---|---|---|
| `hello`   | `{"type":"hello","state":"active"\|"background"}` | first message on connect |
| `state`   | `{"type":"state","state":"active"\|"background"}` | app foreground/background |
| `ack`     | `{"type":"ack","id":"<id>"}` | received `notif` |
| `dismiss` | `{"type":"dismiss","id":"<id>"}` | user dismissed on watch → cancel on Android |
| `action`  | `{"type":"action","id":"<id>","idx":<int>,"label":"<label>","text":"<string>"?}` | run Android action `idx`; `text` fills RemoteInput |
| `findphone` | `{"type":"findphone","on":<bool>}` | start/stop ringing the phone |
| `media`   | `{"type":"media","cmd":"toggle"\|"play"\|"pause"\|"next"\|"prev"\|"vol","v":<0.0-1.0>?}` | media control; `v` only with `vol` |

`hello` additionally accepts an optional `"cal":"<h>"` field: the hash of the calendar the
watch has cached (omit when it has none).

Phone → watch:

| type | fields | meaning |
|---|---|---|
| `welcome` | `{"type":"welcome"}` | reply to `hello` |
| `notif`   | `{"type":"notif", ...notification payload fields (i,p,a,t,b,w,x)...}` | new/updated notification |
| `remove`  | `{"type":"remove","id":"<id>"}` | notification cancelled on Android |
| `sync`    | `{"type":"sync","ids":["<id>",...]}` | ids currently active on Android; sent right after `welcome` |
| `status`  | `{"type":"status","bt":<0-100>,"bc":<bool>}` | phone battery level + charging |
| `media_state` | `{"type":"media_state","on":<bool>,"app":"<label>","t":"<title>","ar":"<artist>","pl":<bool>,"v":<0-1>}` | media session state; strings may be empty when `on=false`; `v` = music stream volume |
| `findphone_state` | `{"type":"findphone_state","on":<bool>}` | whether the phone is currently ringing |
| `cal`     | `{"type":"cal","h":"<hash>","from":<ms>,"to":<ms>,"ev":[...]}` | calendar events, see below |

### Calendar (`cal` message)

`ev` is a list of event objects (max 300, sorted by `s` then `k`):

```json
{"k":"<key>","t":"<title>","s":<startMs>,"e":<endMs>,"ad":<bool allDay>,"loc":"<location>",
 "n":"<notes>","cal":"<calendar name>","col":<int ARGB>,"rm":[<minutes before>...]}
```

- `k` = first 16 chars of `base64url(sha256(utf8("<eventId>|<beginMs>")))`.
- `t` ≤ 200 code points, `n` ≤ 300, `loc` ≤ 200. `rm` = distinct reminder minutes, sorted.
- `h` = first 16 chars of `base64url(sha256(utf8(<exact JSON string of the ev array as sent>)))`.
  The watch treats it as opaque and echoes it in `hello.cal`.
- All-day events: Android stores them at UTC midnight; `s`/`e` are sent as-is with `ad:true`.
  The watch interprets all-day dates in UTC (display the date only) and computes reminder
  times from the LOCAL midnight of that UTC calendar date.

Rules:

- The phone **sends nothing** to a connection until it receives a valid `hello` (decrypts and
  parses). This makes AES-GCM with `encKey` the mutual authentication — no Bluetooth bonding,
  no system pairing dialog.
- The phone ignores anything that fails to decrypt.
- On `hello` the phone replies, in order: `welcome`, `sync`, `status`, `media_state`,
  `cal` (only if the current `h` differs from `hello.cal`, and only when the calendar
  permission is granted), and `findphone_state` (only if currently ringing).
- While authenticated the phone pushes updates: `status` whenever battery level or
  charging changes; `media_state` on metadata/playback changes and after any `media`
  command (debounced 300 ms); `cal` when the calendar provider changes and the new `h`
  differs from the last `h` sent to that connection (debounced 3 s);
  `findphone_state` on change.
- The phone sends `notif`/`remove` one at a time over BLE, waiting for the notification-sent
  callback before the next write; the watch `ack`s each `notif`. If no ack within ~3 s the
  phone falls back to the relay for that notification.

## Relay HTTP API

The relay forwards opaque ciphertext to APNs. It sees `pairId`, `sha256(secret)`, the APNs
device token, the notification `id`, and sealed ciphertext — never plaintext, never `encKey`,
never `K`.

All endpoints are `POST` with a JSON body (max 8 KB) unless noted. Errors are
`{"error":"<message>"}` with a non-2xx status. `GET /healthz` → `200 "ok"` (text/plain).

Rate limits: 600 req/min per IP; 20 register per hour per IP; 120 push per minute per pairId.

### POST /v1/register

```json
{"pairId":"<22 chars>","secret":"<43 chars>","token":"<64-200 hex>","env":"production"|"sandbox"?}
```

- `env` defaults to the server's `APNS_ENV`. The watch sends `sandbox` for DEBUG builds.
- Unknown `pairId`: stores `{token, env, sha256(secret), created, updated}` — **trust on first use**.
- Known `pairId`: `secret` must match (constant-time) → `401` otherwise; updates `token`/`env`.
- → `200 {"ok":true}`

### POST /v1/push

```json
{"pairId":"...","secret":"...","kind":"alert"|"remove","id":"<id>","c":"<base64url sealed, 1-3000>"}
```

- Unknown `pairId` → `404 {"error":"not registered"}`; bad `secret` → `401`.
- `kind=alert`: APNs `push-type: alert`, priority 10, `apns-collapse-id: <id>`, expiration
  now+86400 s. Payload:
  `{"aps":{"alert":{"title":"OpiConnect","body":"New notification"},"mutable-content":1,"sound":"default"},"c":"<c>"}`
- `kind=remove`: APNs `push-type: background`, priority 5, no collapse id, expiration now+3600 s.
  Payload: `{"aps":{"content-available":1},"c":"<c>"}`
- `apns-topic` = `APNS_TOPIC` (the watch app bundle id) for both.
- APNs `200` → `{"ok":true}`. APNs `410`, or `400` with `BadDeviceToken`/`DeviceTokenNotForTopic`
  → pairing deleted, `410 {"error":"gone"}`. Other APNs errors → `502 {"error":"<reason>"}`.

### POST /v1/unregister

`{"pairId":"...","secret":"..."}` → deletes the pairing; `200 {"ok":true}` (idempotent;
`401` on wrong secret for an existing pairing).
